# 场景化系统设计接口与典型日输入规范

## 1. 背景与目标

中期要求强调“单元模块库构建”和“通过调用单元模块库实现系统设计”。这里的重点不是立即实现任意拓扑自动生成，而是先建立一套可复用的场景化系统设计接口：用户给定场景、系统结构、负荷数据和设备边界后，程序调用单元模块库完成双层优化，并输出设备容量配置结果。

本接口设计服务两个阶段：

1. **????**???????????????????????????????????-??????????????????????
2. **后续阶段**：扩展到 15 种以上应用场景，新增场景时尽量只新增配置和数据，不重复开发设备模型。

当前设计口径是：**以应用场景适配能力为主，系统结构差异作为加分项，不强制每个场景都不同拓扑。**

## 2. 核心设计原则

### 2.1 模板优先，降低试用门槛

用户不从空白拓扑开始，而是先选择一个常见系统架构模板。模板自动带出默认能源母线、默认设备组合和默认连接关系。

示例模板：

| 模板 ID | 名称 | 适用场景 | 优先级 |
|---|---|---|---|
| `cchp_ehc_base` | 电-热-冷-气 CCHP 基础系统 | 德国、松山湖基础系统 | 第一版必须跑通 |
| `cchp_ehc_carnot` | 电-热-冷-气 CCHP + 卡诺电池 | 含卡诺电池扩展实验 | 第一版建议跑通 |
| `electric_heat_base` | 电-热系统 | 无冷负荷或电热园区 | 预留 |
| `electric_cooling_base` | 电-冷系统 | 冷主导且无供热需求场景 | 预留 |

### 2.2 默认设备库补齐参数

用户最小只需要声明设备是否启用、是否参与容量优化和容量上限。设备效率、投资成本、运维成本、排放因子等由内置参数库补齐。

用户如果有工程实测或项目要求参数，可以在场景配置中覆盖默认值。

```yaml
devices:
  chp:
    library_id: chp_gas_turbine
    enabled: true
    optimize_capacity: true
    capacity_ub_kw: 800
    eta_e: 0.35      # 可选覆盖默认值
    eta_h: 0.45      # 可选覆盖默认值
```

### 2.3 设备按类型抽象，不按场景重复建模

设备库按“源、荷、储、转”类型组织。场景只负责选择设备组合和填写参数，不为每个场景复制一套设备模型。

```text
源侧设备：电网、天然气、光伏、风电、外部热源、外部冷源
转换设备：CHP、电热泵、电制冷机、吸收式制冷机、电解槽、燃料电池 CHP
储能设备：电储能、热储能、冷储能、储氢、卡诺电池
负荷设备：电负荷、热负荷、冷负荷、柔性负荷
```

### 2.4 输入分为内部标准配置和展示 Excel 模板

第一版同时支持两类用户：

| 用户类型 | 推荐输入 | 说明 |
|---|---|---|
| 内部开发者 | YAML/JSON + CSV | 程序真正读取的标准格式，适合长期扩展。 |
| 展示/验收用户 | Excel 模板 | 参考 `松山湖社区方案-0901.xls`，方便非代码用户填写。 |

Excel 模板不直接等同于计算模型。推荐流程是：

```text
展示 Excel
  -> 转换脚本
  -> 标准 YAML/CSV 场景包
  -> 调用单元模块库和优化模型
```

## 3. 用户最小输入

第一版用户最小需要提供 5 类输入。

### 3.1 场景基本信息

```yaml
scenario:
  id: songshan_lake
  name: 松山湖科研产业园
  currency: CNY
  location: dongguan
```

最小必填字段：

| 字段 | 是否必填 | 说明 |
|---|---|---|
| `scenario.id` | 是 | 场景唯一编号，用于结果目录和配置引用。 |
| `scenario.name` | 是 | 场景中文名或项目名。 |
| `currency` | 是 | 成本输出币种，例如 CNY、EUR、USD。 |
| `location` | 否 | 地区信息，用于报告和默认气象参数选择。 |

### 3.2 系统结构模板

```yaml
system:
  template: cchp_ehc_base
  energy_carriers: [electricity, heat, cooling, gas]
```

用户暂时不需要提供详细拓扑连接表。第一版由模板固定连接关系。

### 3.3 负荷与资源数据

程序内部标准列建议为：

```csv
time,ele_load_kw,heat_load_kw,cool_load_kw,solar_radiation_w_m2,wind_speed_m_s,temperature_c
```

规则：

1. 场景存在的负荷必须提供。
2. 启用设备需要的资源数据必须提供。
3. 未启用设备对应资源可以不填或填 0。
4. 第一版为简化读取，标准 CSV 可以固定列，不需要的列填 0。

### 3.4 仿真范围与年化方式

```yaml
simulation:
  mode: typical_days
  annualization: weighted
```

支持三种模式：

| 模式 | 输入 | 年化方式 | 说明 |
|---|---|---|---|
| `timeseries_8760` | 8760 逐时数据 | `full_year` | 高精度输入，可直接全年后分析，也可自动聚类。 |
| `typical_days` | 典型日曲线 + 权重 | `weighted` | 中期和当前优化主推模式。 |
| `short_period` | 一天、一周或一个月 | `none` 或用户指定权重 | 用于接口试跑，不默认宣称全年最优。 |

### 3.5 设备配置与容量边界

```yaml
devices:
  pv:
    library_id: pv_standard
    enabled: true
    optimize_capacity: true
    capacity_ub_kw: 1000

  wind:
    library_id: wind_turbine
    enabled: false
    optimize_capacity: false
    capacity_ub_kw: 0
```

最小必填字段：

| 字段 | 是否必填 | 说明 |
|---|---|---|
| `library_id` | 是 | 引用默认设备库。 |
| `enabled` | 是 | 是否启用该设备。 |
| `optimize_capacity` | 是 | 是否由容量优化决定容量。 |
| `capacity_ub_kw` | 是 | 容量优化上界。 |
| 技术经济参数 | 否 | 默认库补齐，用户可覆盖。 |

## 4. 场景包目录建议

每个应用场景建议整理成一个独立场景包。

```text
scenarios/songshan_lake/
├── scenario.yaml          # 场景、系统模板、仿真设置、设备覆盖参数
├── load_timeseries.csv    # 8760 数据或标准时序数据
├── typical_days.csv       # 典型日权重文件，可由程序生成
├── typical_profiles.csv   # 月典型日或聚类典型日 24h 曲线
├── raw_input.xlsx         # 展示/验收 Excel，可选
└── README.md              # 场景说明和数据来源
```

当前已有德国和松山湖可以先映射为两个场景包，底层仍复用现有 `case_config.py`、`cchp_gaproblem.py` 和 `operation.py`，后续再逐步迁移到标准接口。

## 5. Excel 展示模板设计

Excel 主推“月度总量 + 每月 1 个典型日 24h 曲线”。这与 `松山湖社区方案-0901.xls` 的工程数据形式接近，便于中期展示和第三方验收。

推荐 sheet：

| Sheet | 是否必填 | 作用 |
|---|---|---|
| `01_场景信息` | 是 | 场景编号、名称、地区、币种、说明。 |
| `02_仿真设置` | 是 | 仿真模式、年化方式、是否自动生成典型日。 |
| `03_月度能源量` | 是，月典型日模式 | 每月电/热/冷总量、天数。 |
| `04_典型日负荷` | 是，月典型日模式 | 12 个月各 1 个 24h 典型日曲线。 |
| `05_资源数据` | 视设备而定 | 光伏、风电、温度等资源曲线或单位装机出力。 |
| `06_设备配置` | 是 | 设备启停、是否优化、容量上界。 |
| `07_价格参数` | 是 | 电价、气价、容量费等。 |
| `08_设备参数覆盖` | 否 | 覆盖默认设备库参数。 |
| `09_输出说明` | 否 | 用户希望导出的结果类型。 |

### 5.1 月度能源量表

```csv
month,days,ele_energy_kwh,heat_energy_kwh,cool_energy_kwh,public_ele_kwh,hvac_ele_kwh
1,31,...
2,28,...
```

### 5.2 每月 1 个典型日负荷表

```csv
profile_id,month,hour,ele_load_kw,heat_load_kw,cool_load_kw
M01,1,1,...
M01,1,2,...
...
M12,12,24,...
```

权重规则：

```text
M01 权重 = 1 月天数
M02 权重 = 2 月天数
...
M12 权重 = 12 月天数
```

即：12 个典型日代表全年 365 天。

## 6. 典型日生成与聚类接口

用户提供 8760 数据时，系统应支持多种典型日生成方式，由用户配置选择。典型日生成模块建议独立为：

```text
TypicalDayGenerator / 典型日生成器
```

### 6.1 典型日来源类型

| 来源 | 配置值 | 说明 |
|---|---|---|
| 用户已有典型日文件 | `user_selected` | 兼容当前 `typicalDayData.xlsx` 和 `songshan_lake_typical.xlsx`。 |
| Excel 月典型日 | `monthly_template` | 每月 1 个 24h 典型日，权重为该月天数。 |
| 从 8760 自动聚类 | `cluster_from_8760` | 程序根据全年逐时数据生成典型日。 |
| 月内自动选代表日 | `monthly_medoid` | 每个月从真实日中选 1 个最接近月平均形状的代表日。 |

### 6.2 支持的聚类方式

| 方法 | 配置值 | 推荐用途 | 说明 |
|---|---|---|---|
| K-Medoids | `kmedoids` | 默认正式方法 | 代表日是真实日，和当前论文口径最一致。 |
| K-Means + 近中心真实日 | `kmeans_medoid` | 通用依赖方案 | 先 K-Means 聚类，再选距中心最近的真实日。 |
| 层次聚类 + 近中心真实日 | `hierarchical` | 兜底方案 | 不依赖 `sklearn_extra`，适合 365 天小样本。 |
| 月度代表日 | `monthly_medoid` | 工程解释性强 | 每月选 1 个真实代表日，得到 12 个代表日。 |
| 用户指定 | `user_selected` | 已有聚类结果或专家指定 | 用户直接给典型日文件。 |

### 6.3 推荐配置字段

```yaml
simulation:
  mode: typical_days
  annualization: weighted

typical_day:
  source: cluster_from_8760
  method: kmedoids
  n_typical_days: 14
  feature_policy: auto
  feature_columns: []
  normalize: standard
  representative: medoid
  random_seed: 42
  fallback_method: kmeans_medoid
  output_file: typical_days.csv
```

如果用户用 Excel 月典型日模板：

```yaml
typical_day:
  source: monthly_template
  profiles_per_month: 1
  weight_policy: month_days
```

如果用户已有典型日文件：

```yaml
typical_day:
  source: user_selected
  file: data/typical_days.csv
```

### 6.4 聚类特征选择规则

默认使用 `feature_policy: auto`。程序根据系统模板和启用设备自动选择特征。

| 场景 | 推荐特征 |
|---|---|
| 德国 CCHP | 电负荷、热负荷、冷负荷、太阳辐射、风速、温度 |
| 松山湖 CCHP | 电负荷、热负荷、冷负荷、太阳辐射、温度 |
| 电-热系统 | 电负荷、热负荷、太阳辐射、温度 |
| 电-冷系统 | 电负荷、冷负荷、太阳辐射、温度 |

原则：

1. 启用 PV 时加入太阳辐射或单位装机光伏出力。
2. 启用风电时加入风速或单位装机风电出力。
3. 温度默认加入，因为它影响冷热负荷和空调形态。
4. 未启用设备对应资源不参与聚类，避免无意义特征干扰。

### 6.5 统一输出格式

无论采用哪种方式，典型日生成器都应输出统一文件，兼容当前代码前三列。

```csv
typicalDayId,weight,days,method,source,feature_columns
29,18,"3,12,29,45",kmedoids,cluster_from_8760,"ele_load,heat_load,cool_load,solar,temperature"
```

当前代码至少需要：

```csv
typicalDayId,weight,days
```

扩展字段用于报告和审计，不应破坏旧代码读取。

## 7. 当前实验口径与新接口映射

当前论文实验并不是完整 8760 小时连续优化，而是：

```text
8760 原始数据
  -> 典型日文件
  -> 优化阶段只调度典型日 24h
  -> 典型日结果按代表天数回填/加权
  -> 得到年化成本和全年等效匹配指标
```

在新接口中可表述为：

```yaml
simulation:
  mode: typical_days
  annualization: weighted

typical_day:
  source: cluster_from_8760
  method: kmedoids
  n_typical_days: 14
```

后验分析阶段则可单独配置为：

```yaml
post_analysis:
  enabled: true
  mode: daily_8760
  description: 使用全年8760原始数据逐日调度，计算运行指标
```

需要注意：后验分析是 365 天逐日 24h 调度，不等同于一个完整 8760h 连续调度模型。

## 8. 输出结果规范

第一版输出不应只保留论文实验的 Pareto 表，还应形成“系统设计交付物”。

| 输出文件 | 作用 |
|---|---|
| `design_summary.csv/json` | 推荐容量配置结果。 |
| `pareto_solutions.csv` | Pareto 解集，包含成本、匹配度和设备容量。 |
| `objective_values.csv` | 目标函数值、可行性标记。 |
| `operation_summary.csv` | 年购电量、购气量、自给率、弃能率、电网波动等。 |
| `dispatch_timeseries/` | 选定方案的逐时调度结果，可选。 |
| `design_report.md` | 面向中期/验收的文字报告。 |
| `typical_day_report.md` | 典型日来源、方法、特征列、权重统计。 |

报告中必须记录典型日来源，避免把月典型日、聚类典型日和短周期测试混为一谈。

## 12. `scenario.yaml` 字段规范

`scenario.yaml` 是内部开发者主要使用的场景配置入口。它不把所有数据写进一个文件，而是负责描述场景身份、系统模板、数据路径、典型日来源、设备配置、优化参数和输出设置。

### 12.1 推荐完整结构

```yaml
schema_version: "1.0"

scenario:
  id: songshan_lake
  name: 松山湖科研产业园
  description: 冷主导园区综合能源系统设计场景
  location: dongguan
  currency: CNY

system:
  template: cchp_ehc_base
  energy_carriers: [electricity, heat, cooling, gas]

data:
  input_type: timeseries_8760
  load_file: load_timeseries.csv
  time_column: time
  timezone: Asia/Shanghai
  column_mapping:
    ele_load_kw: ele_load(kW)
    heat_load_kw: heat_load(kW)
    cool_load_kw: cool_load(kW)
    solar_radiation_w_m2: solarRadiation(W/m-2)
    wind_speed_m_s: windSpeed(m/s)
    temperature_c: temperature(C)

simulation:
  mode: typical_days
  annualization: weighted
  time_step_hours: 1
  dispatch_horizon_hours: 24

typical_day:
  source: cluster_from_8760
  method: kmedoids
  n_typical_days: 14
  feature_policy: auto
  normalize: standard
  representative: medoid
  random_seed: 42
  fallback_method: kmeans_medoid
  output_file: typical_days.csv

prices:
  electricity:
    type: flat
    unit: CNY_per_kWh
    value: 0.6746
  gas:
    type: flat
    unit: CNY_per_kWh
    value: 0.45
  capacity_charge:
    unit: CNY_per_kW_year
    value: 0

devices:
  pv:
    library_id: pv_standard
    enabled: true
    optimize_capacity: true
    capacity_ub_kw: 1000
  wind:
    library_id: wind_turbine
    enabled: false
    optimize_capacity: false
    capacity_ub_kw: 0
  chp:
    library_id: chp_gas_turbine
    enabled: true
    optimize_capacity: true
    capacity_ub_kw: 800
    overrides:
      eta_e: 0.35
      eta_h: 0.45

optimization:
  objectives: [annual_cost, source_load_matching]
  matching_method: euclidean
  algorithm: nsga2
  nind: 10
  maxgen: 5
  pool_type: Process
  workers: 4

post_analysis:
  enabled: false
  mode: daily_8760
  selected_solutions: knee

output:
  root_dir: DesignResults
  save_raw_results: true
  save_dispatch_timeseries: false
  report_language: zh
```

### 12.2 顶层字段说明

| 字段 | 是否必填 | 说明 |
|---|---|---|
| `schema_version` | 是 | 配置文件版本，用于后续兼容。 |
| `scenario` | 是 | 场景身份信息，用于报告和结果目录。 |
| `system` | 是 | 系统结构模板和能源载体。 |
| `data` | 是 | 负荷、资源、Excel 或典型日数据路径。 |
| `simulation` | 是 | 优化阶段采用的时间尺度和年化方式。 |
| `typical_day` | 视模式而定 | 典型日来源、聚类方法和输出文件。 |
| `prices` | 是 | 电价、气价、容量电费等能源价格。 |
| `devices` | 是 | 设备启停、容量边界和用户参数覆盖。 |
| `optimization` | 是 | 优化算法、目标函数、种群规模和并行设置。 |
| `post_analysis` | 否 | 后验 8760 逐日调度分析设置。 |
| `output` | 否 | 输出目录和报告设置。 |

### 12.3 支持的数据输入类型

| `data.input_type` | 含义 | 典型用途 |
|---|---|---|
| `timeseries_8760` | 用户提供全年 8760 逐时数据。 | 当前德国、松山湖论文数据。 |

| `typical_day.source` | 含义 |
|---|---|
| `user_selected` | 用户已有典型日文件，直接读取。 |

## 13. 多场景自适应 Excel/YAML 输入规范

### 13.1 为什么要从固定冷热电模板升级

`../课题组场景整理/15种场景+8种能源转换类型-2024092.xlsx` 中的 15 种应用场景并不都只有电、热、冷需求。不同场景可能包含氢、蒸汽、天然气、甲醇、氧等用户需求，也可能包含地热、余热、生物质、潮汐等能源输入或资源条件。

因此，Excel 和 YAML 不能写死为：

```text
ele_load_kw, heat_load_kw, cool_load_kw
```

而应改为“能源载体可配置”的通用格式。用户先声明当前场景有哪些用户负荷需求、有哪些能源输入和资源条件，再分别填写对应数据。

核心原则：

```text
用户负荷需求 demand：用户需要被满足的能源服务。
能源输入/资源 supply/resource：系统可以利用、购买或转化的能源来源。
设备库 device：把输入/资源转化为用户需求的模块。
```

### 13.2 输入和负荷必须分开

为避免用户混淆，Excel 中应明确把“用户负荷需求”和“能源输入/资源条件”拆成不同 sheet。

| 类型 | 用户需要填写什么 | 示例 |
|---|---|---|
| 用户负荷需求 | 需要系统满足的逐时或月度需求 | 电负荷、热负荷、冷负荷、蒸汽需求、氢需求、天然气需求 |
| 能源输入/资源条件 | 系统可获得的外部能源、自然资源或工业余能 | 电网、天然气、生物质、太阳辐射、风速、余热、地热、潮汐 |
| 设备配置 | 系统允许使用哪些设备把输入转成负荷需求 | 光伏、风机、CHP、电解槽、吸收式制冷机、储氢罐 |

这样用户可以直观看到：

```text
我要提供的需求数据：05_用户负荷需求曲线
我要提供的能源来源数据：06_能源输入与资源曲线
我要提供的设备选择：07_设备配置
```

### 13.3 能源输入和资源是否合并

概念上建议区分，Excel 操作上可以合并到一个 sheet。

#### 概念区分

| 概念 | 含义 | 例子 | 为什么重要 |
|---|---|---|---|
| 能源输入 `energy_input` | 可以直接进入系统能源平衡或被购买的能源载体 | 电网购电、天然气、外购氢、生物质燃料 | 需要价格、排放因子、购买上限、供应可靠性。 |
| 资源条件 `resource` | 不能直接满足负荷，需要设备转化的自然资源或条件 | 太阳辐射、风速、环境温度、潮汐资源 | 通常没有直接价格，而是用于计算光伏、风电、热泵等设备出力。 |
| 可回收能源 `recoverable_energy` | 场景中可利用但受工况限制的余能 | 工业余热、余压、废气热量 | 可能既像资源，又像能源输入，需要可用量、温度品位和时间曲线。 |

例如：

```text
太阳辐射不是电能输入，必须经过光伏设备才变成电。
天然气是燃料输入，可以直接进入 CHP 或锅炉。
余热可以视为可回收能源，需要通过余热锅炉、吸收式制冷等设备利用。
```

#### Excel 操作合并

为了让用户少填表，第一版可以把能源输入、资源条件和可回收能源放在同一个 sheet：

```text
06_能源输入与资源曲线
```

但必须用字段区分类型：

```text
input_id,input_name,input_type,carrier_id,profile_id,month,hour,value,unit,remark
```

其中 `input_type` 可取：

| `input_type` | 含义 | 示例 |
|---|---|---|
| `purchased_energy` | 可购买能源输入 | grid_electricity, natural_gas, external_hydrogen |
| `renewable_resource` | 可再生自然资源 | solar_resource, wind_resource, tidal_resource |
| `recoverable_energy` | 可回收能源 | waste_heat, waste_pressure |
| `environment` | 环境条件 | temperature |

这样既保持用户填写简单，又保证程序内部能正确处理价格、排放、设备出力模型和约束。

### 13.4 建议的 Excel sheet 结构

最终 Excel 模板建议为：

```text
01_场景信息
02_仿真设置
03_场景能源配置
04_月度用户需求
05_用户负荷需求曲线
06_能源输入与资源曲线
07_设备配置
08_价格与排放参数
09_设备参数覆盖
10_输出设置
11_填写说明
```

与前一版相比，关键变化是：

1. `03_场景能源配置` 声明当前场景有哪些需求、输入和资源。
2. `04_月度用户需求` 只填用户需求，不填能源输入。
3. `05_用户负荷需求曲线` 只填用户需求曲线。
4. `06_能源输入与资源曲线` 填电网、天然气、太阳辐射、风速、余热、地热等供给侧信息。

用途：让用户和程序明确当前场景包含哪些能源需求、输入和资源。

| 字段 | 说明 |

### 13.8 `06_能源输入与资源曲线`

用途：记录系统可利用的能源输入、可再生资源、可回收余能和环境条件。

固定列：

```csv

```

示例：


### 13.10 通用长表与当前 CCHP 模型的适配

长期标准输入应使用通用长表：


但当前优化内核 `operation.py` / `cchp_gaproblem.py` 只支持电、热、冷和燃气燃料。因此第一版需要增加适配器：

```text

  -> 当前 CCHP 专用 CSV
  -> 调用现有优化模型
```

当前 CCHP 专用 CSV 仍为：

```csv

```

### 13.11 第一版计算能力边界

第一版接口规范预留多能源载体，但计算内核优先支持：

```text
electricity, heat, cooling, natural_gas fuel, solar_resource, wind_resource, temperature
```

以下载体先完成输入规范预留，等新增设备模型和系统模板后再真正参与优化：

```text
hydrogen, steam, methanol, oxygen, natural_gas demand, biomass, geothermal, tidal, waste_heat
```

这意味着：

1. 德国和松山湖冷热电场景可以直接跑通。
2. 电-冷、电-热简化场景可通过模板简化后接入。
3. 加氢站、钢铁、油田、海岛等场景可先使用同一输入模板整理数据，但需要后续补充氢、蒸汽、甲醇等设备模块后才能完整优化。

## 15. `device_library.yaml` 默认设备库设计

多场景输入模板改为可扩展能源载体后，设备库必须承担“能源载体连接关系”的定义职责。也就是说，用户可以只选择设备，设备库负责说明该设备消耗什么、产出什么、有哪些容量变量、默认技术经济参数是什么。

### 15.1 设备库设计目标

`device_library.yaml` 需要回答五个问题：

1. 这个设备属于源、荷、储、转哪一类。
2. 这个设备的输入能源载体是什么。
3. 这个设备的输出能源载体是什么。
4. 这个设备有哪些容量变量和默认容量单位。
5. 这个设备有哪些默认技术经济参数，可被用户覆盖。

这样用户在 Excel 或 `scenario.yaml` 中只需要写：

```yaml
devices:
  chp:
    library_id: chp_gas_turbine
    enabled: true
    optimize_capacity: true
    capacity_ub_kw: 800
```

程序就可以从设备库补齐：

```text
input_carriers = [natural_gas]
output_carriers = [electricity, heat]
eta_e = 0.35
eta_h = 0.45
invest_coeff = 默认值
```

### 15.3 载体字典 `carrier_dictionary`

载体字典统一约束能源载体名称、默认单位和类别，避免用户在不同场景中写出多个同义字段。

| 字段 | 说明 |
|---|---|
| `name` | 中文显示名。 |
| `default_unit` | 默认单位。 |
| `category` | `energy_carrier`、`renewable_resource`、`recoverable_energy`、`environment`。 |
| `aliases` | 可选，用户 Excel 中可能出现的别名。 |
| `conversion` | 可选，单位换算规则。 |

示例：

```yaml
carrier_dictionary:
  hydrogen:
    name: 氢
    default_unit: kg/h
    category: energy_carrier
    aliases: [氢气, H2, hydrogen]
  steam:
    name: 蒸汽
    default_unit: t/h
    category: energy_carrier
    aliases: [汽, 工业蒸汽, steam]
```

第一版可以先只做名称校验，不做复杂单位换算。单位换算可作为后续增强。

### 15.4 设备条目通用字段

每个设备条目建议包含：

```yaml
devices:
  device_library_id:
    name: 设备名称
    abstract_type: 抽象设备类型
    unit_group: source | converter | storage | load | external
    input_carriers: []
    output_carriers: []
    capacity: {}
    parameters: {}
    constraints: {}
    economics: {}
    carbon: {}
    implementation:
      status: implemented | reserved | planned
      backend: current_cchp | future_generic | external
```

字段说明：

| 字段 | 说明 |
|---|---|
| `abstract_type` | 抽象设备类型，如 `renewable_power`、`cogeneration`、`power_to_heat`。 |
| `unit_group` | 源、转、储、荷或外部能源接口。 |
| `input_carriers` | 输入能源载体或资源。 |
| `output_carriers` | 输出能源载体。 |
| `capacity` | 容量变量定义。 |
| `parameters` | 技术参数。 |
| `constraints` | 运行或设计约束。 |
| `economics` | 投资、运维、燃料等经济参数。 |
| `carbon` | 排放因子或碳核算参数。 |
| `implementation.status` | 当前是否已被计算内核支持。 |
| `implementation.backend` | 对应哪个计算后端。 |

### 15.7 用户参数覆盖优先级

设备参数合并顺序应固定，避免多处配置冲突。

```text
device_library.yaml 默认值
  -> system_templates.yaml 模板默认值
  -> scenario_catalog.yaml 场景类型默认值
  -> scenario.yaml 用户覆盖
  -> Excel `09_设备参数覆盖` 覆盖
```

后面的优先级更高。最终应输出：

```text
resolved_scenario.yaml
```

用于记录所有默认值和用户覆盖后的最终计算配置。

### 15.8 与当前 `case_config.py` 的适配

当前优化内核仍需要 `case_config.py` 风格字段，例如：

```python
var_ub = [ppv, pwt, pgt, php, pec, pac, pes, phs, pcs]
invest_coeff = [pv, wt, gt, hp, ec, ac, es, hs, cs]
gt_eta_e, gt_eta_h, ac_cop, ehp_cop, ec_cop
```

因此第一版应实现一个适配器：

```text
resolved_scenario.yaml + device_library.yaml
  -> current_cchp_case_config dict
  -> CCHPProblem / OperationModel
```

映射关系示例：

| 当前字段 | 来源 |
|---|---|
| `var_ub[0]` | `devices.pv.capacity_ub_kw` |
| `var_ub[1]` | `devices.wind.capacity_ub_kw` |
| `var_ub[2]` | `devices.chp.capacity_ub_kw` |
| `gt_eta_e` | `devices.chp.overrides.eta_e` 或设备库默认值 |
| `gt_eta_h` | `devices.chp.overrides.eta_h` 或设备库默认值 |
| `ec_cop` | `devices.electric_chiller.overrides.cop` 或设备库默认值 |
| `enable_carnot_battery` | `devices.carnot_battery.enabled` |

### 15.9 校验规则

加载设备库和场景配置时应至少做以下校验：

1. `library_id` 必须存在于 `device_library.yaml`。
2. 启用设备的 `input_carriers` 和 `output_carriers` 必须能在场景能源配置中找到。
3. 启用设备需要的资源或能源输入必须有数据或价格配置。
4. 被声明为用户需求的 `demand_id` 必须出现在负荷曲线中。
5. 当前计算后端不支持的设备，如果 `enabled=true` 且参与优化，应给出明确错误或提示“接口预留，尚未实现”。
6. 当前 CCHP 后端只允许启用 `implementation.backend=current_cchp` 的设备。

### 15.10 中期落地建议

中期第一版可以采用两层设备库策略：

```text
第一层：完整设备库规范，预留 15 种场景需要的设备类型。
第二层：当前 CCHP 可计算设备子集，用于德国和松山湖跑通。
```

这样汇报时可以说明：

```text
设备库接口已按多场景通用需求预留氢、蒸汽、余热、地热等设备类型；当前计算内核已完成冷热电 CCHP 设备子集调用验证，后续新增设备模型后可复用同一接口扩展到更多场景。
```

## 16. `system_templates.yaml` 系统结构模板设计

`device_library.yaml` 定义“设备能做什么”，`system_templates.yaml` 定义“一个系统结构默认包含哪些能源母线、哪些设备、哪些连接关系和哪些优化变量”。第一版暂不做任意拓扑自动生成，而是通过预置系统模板降低用户使用门槛。

### 16.1 设计目标

系统模板需要回答四个问题：

1. 该系统包含哪些能源载体和母线。
2. 默认启用哪些设备，哪些设备可选。
3. 设备如何连接到能源载体。
4. 如何映射到当前计算后端，例如当前 CCHP 后端。

### 16.6 模板与当前 CCHP 后端的边界

当前 `current_cchp` 后端只支持：

```text
electricity, heat, cooling, natural_gas, solar_resource, wind_resource, temperature
```

且设备变量顺序固定为：

```text
[pv, wind, chp, electric_heat_pump, electric_chiller, absorption_chiller, electric_storage, heat_storage, cold_storage]
```

启用卡诺电池时追加：

```text
[carnot_battery_power, carnot_battery_capacity]
```

1. `supported_backend=current_cchp` 的模板可以直接调用现有代码。
2. `supported_backend=future_generic` 的模板只完成接口预留，需后续通用建模器支持。
3. 如果用户启用了 current_cchp 不支持的设备，应在校验阶段报错，而不是运行到优化阶段才失败。

## 17. 设备到 Pyomo/OEMOF 组件的建模抽象

### 17.1 设备库不是求解器组件

设备库中的“设备”是接口层抽象，不是直接的 Pyomo 或 OEMOF 对象。真实建模时，需要根据设备的抽象类型、输入输出载体、容量变量和参数，将设备转换成一个或多个建模组件。

可以理解为三层：

```text
场景设备配置 device instance
  -> 设备抽象类型 device abstract type
  -> 建模组件 mapping to oemof/pyomo component
```

例如：

```text
chp_gas_turbine
  -> cogeneration 抽象类型
  -> OEMOF Transformer，输入 gas_bus，输出 ele_bus + heat_bus
```

```text
electric_storage
  -> storage 抽象类型
  -> OEMOF GenericStorage，连接 ele_bus
```

```text
pv_standard
  -> renewable_power 抽象类型
  -> OEMOF Source，fix profile = PV可用出力，nominal_capacity = 优化容量
```

这就是接口层抽象的意义：不同具体设备可以复用少数几类建模模式。

### 17.2 推荐的三层抽象

#### 第一层：具体设备实例

来自用户场景配置。

```yaml
devices:
  chp:
    library_id: chp_gas_turbine
    enabled: true
    capacity_ub_kw: 800
    overrides:
      eta_e: 0.35
      eta_h: 0.45
```

这一层回答：

```text
这个场景里有没有这台设备，容量边界是多少，是否覆盖默认参数。
```

#### 第二层：设备抽象类型

来自设备库。

```yaml
chp_gas_turbine:
  abstract_type: cogeneration
  input_carriers: [natural_gas]
  output_carriers: [electricity, heat]
```

这一层回答：

```text
这类设备的能量转换逻辑是什么。
```

#### 第三层：建模组件映射

来自建模器或 `component_mapping.yaml`。

```yaml
component_mappings:
  cogeneration:
    oemof_component: Transformer
    input_ports: [fuel]
    output_ports: [electricity, heat]
    parameter_mapping:
      eta_e: conversion_factors.electricity
      eta_h: conversion_factors.heat
```

这一层回答：

```text
如何把抽象设备翻译成 OEMOF/Pyomo 可求解对象。
```

### 17.3 常见抽象类型到组件的映射

| 抽象类型 | 可覆盖设备 | OEMOF/Pyomo 建模组件 | 说明 |
|---|---|---|---|
| `external_source` | 电网、天然气管网、外购氢 | `Source` | 可购买能源，通常有 variable_costs。 |
| `fixed_load` | 电负荷、热负荷、冷负荷、氢需求 | `Sink` | 固定需求曲线。 |
| `renewable_power` | 光伏、风电、潮汐发电 | `Source` | 固定可用曲线 + 容量变量。 |
| `renewable_heat` | 地热、太阳能集热 | `Source` 或 `Transformer` | 取决于是否需要泵耗或转换效率。 |
| `cogeneration` | 燃气 CHP、燃料电池 CHP、生物质 CHP | `Transformer` | 单输入，多输出。 |
| `power_to_heat` | 电热泵、电锅炉 | `Transformer` | 电输入，热输出。 |
| `power_to_cooling` | 电制冷机 | `Transformer` | 电输入，冷输出。 |
| `heat_to_cooling` | 吸收式制冷机 | `Transformer` | 热输入，冷输出。 |
| `power_to_fuel` | 电解槽 | `Transformer` | 电输入，氢/氧输出。 |
| `fuel_to_steam` | 燃气锅炉、生物质锅炉 | `Transformer` | 燃料输入，蒸汽输出。 |
| `storage` | 电储能、热储能、冷储能 | `GenericStorage` | 单一载体充放。 |
| `fuel_storage` | 储氢、储气 | `GenericStorage` 或自定义 Pyomo | 需要质量单位和泄漏约束。 |
| `multi_output_storage` | 卡诺电池 | `GenericStorage` + `Transformer` 或自定义组件 | 电储能并带余热回收。 |
| `recoverable_energy_to_heat` | 余热回收 | `Source` + `Transformer` | 余热可用量作为上限。 |

### 17.4 建议新增 `component_mapping.yaml`

为了把设备库和求解器解耦，建议新增一个映射文件：

```text
ies_design/defaults/component_mapping.yaml
```

示例：

```yaml
schema_version: "1.0"

component_mappings:
  renewable_power:
    backend: oemof
    component: Source
    profile_required: true
    capacity_mode: invest_or_nominal
    ports:
      inputs: []
      outputs: [electricity]
    build_logic: fixed_profile_source

  cogeneration:
    backend: oemof
    component: Transformer
    ports:
      inputs: [fuel]
      outputs: [electricity, heat]
    parameter_mapping:
      eta_e: conversion_factor_electricity
      eta_h: conversion_factor_heat
    build_logic: multi_output_transformer

  storage:
    backend: oemof
    component: GenericStorage
    ports:
      inputs: [carrier]
      outputs: [carrier]
    parameter_mapping:
      charge_efficiency: inflow_conversion_factor
      discharge_efficiency: outflow_conversion_factor
      loss_rate: loss_rate
    build_logic: generic_storage
```

### 17.5 建模器 `ModelBuilder` 的职责

后续通用建模器可以叫：

```text
ModelBuilder / OemofModelBuilder
```

它的职责不是理解每个场景的业务，而是按统一接口把设备实例转成组件。

输入：

```text
resolved_scenario.yaml
system_templates.yaml
device_library.yaml
component_mapping.yaml
standard_timeseries.csv 或 typical_profiles.csv
```

输出：

```text
OEMOF EnergySystem / Pyomo ConcreteModel
```

处理流程：

```text
1. 创建能源母线 buses
2. 创建外部能源 Source
3. 创建用户负荷 Sink
4. 遍历 enabled devices
5. 根据 library_id 找设备抽象类型
6. 根据 abstract_type 找 component_mapping
7. 把设备参数映射成 OEMOF/Pyomo 组件参数
8. 添加容量变量、上下界和约束
9. 返回可求解模型
```

### 17.6 为什么这种抽象有必要

如果不做设备抽象，会出现：

```text
每新增一个设备，就在 operation.py 里手写一段 OEMOF 组件。
每新增一个场景，就复制修改一套系统模型。
```

这样很难扩展到 15 个场景。

抽象之后变成：

```text
新增具体设备：优先新增 device_library 条目。
新增类似设备：复用已有 abstract_type 和 component_mapping。
新增新物理逻辑：新增 abstract_type 和 component_mapping。
新增场景：选择 system_template + devices，不重写建模代码。
```

例如：

```text
燃气 CHP、氢燃料电池 CHP、生物质 CHP
  -> 都是 cogeneration
  -> 都可映射为单输入多输出 Transformer
  -> 差异体现在燃料、效率、成本、排放参数
```

```text
电热泵、电锅炉、电制冷机
  -> 都是电转其他能源的 Transformer
  -> 差异体现在输出载体和 COP/效率
```

### 17.7 当前阶段与未来阶段的区别

第一版为了稳妥，可以暂时不实现完整通用 `ModelBuilder`，而是采用适配器模式：

```text
新接口配置
  -> current_cchp_case_config_adapter
  -> 现有 operation.py
```

这时 `component_mapping.yaml` 可以先作为设计文档和未来接口预留。

后续当要支持氢、蒸汽、甲醇等新场景时，再实现：

```text
新接口配置
  -> OemofModelBuilder
  -> 通用 OEMOF/Pyomo 模型
```

因此中期可以这样表述：

```text
当前版本已完成设备库接口层抽象，并通过适配器映射到现有冷热电 CCHP OEMOF 模型；后续将把抽象设备类型统一映射为 Source、Sink、Transformer、GenericStorage 及必要的自定义 Pyomo 组件，从而支撑氢、蒸汽等扩展场景。
```

### 17.8 校验与报错

建模前应校验：

1. 每个启用设备都能找到 `library_id`。
2. 每个启用设备都声明了 `abstract_type`。
3. 每个 `abstract_type` 都能找到组件映射。
4. 设备输入输出载体都存在对应母线或可由模板创建。
5. 设备所需参数齐全，例如 CHP 必须有 `eta_e` 和 `eta_h`。
6. 当前后端不支持的设备不能直接进入求解。

报错应面向用户，例如：

```text
设备 electrolyzer 已启用，但当前模板 cchp_ehc_base 使用 current_cchp 后端，该后端尚不支持 hydrogen 载体。请关闭 electrolyzer 或切换到支持 hydrogen 的系统模板。
```

## 18. 配置解析与校验流程

程序读取用户输入后，不应直接进入优化，而应先生成一个完整的已解析配置文件：

```text
resolved_scenario.yaml
```

该文件记录所有默认值、模板值、场景类型值和用户覆盖值合并后的最终计算配置，便于复现、排错和中期验收。

### 18.1 推荐解析流程

```text
1. 读取 scenario.yaml 或 Excel
2. 如果是 Excel，先转换成中间 YAML/CSV
3. 读取 scenario_catalog.yaml
4. 读取 system_templates.yaml
5. 读取 device_library.yaml
6. 读取 component_mapping.yaml
7. 根据 scenario_type 补齐默认场景需求和候选设备
8. 根据 system.template 补齐母线、默认设备和模板参数
9. 根据 devices.library_id 补齐设备端口和默认技术经济参数
10. 应用用户在 scenario.yaml / Excel 中的覆盖
11. 校验能源载体、设备、数据列、价格、典型日
12. 输出 resolved_scenario.yaml
13. 转换为 current_cchp case_config 或未来通用模型输入
```

汇总关系：

```text
scenario_catalog 默认场景类型
  + system_templates 默认系统结构
  + device_library 默认设备参数
  + component_mapping 建模映射
  + scenario.yaml 用户配置
  + Excel 用户输入
  ↓
resolved_scenario.yaml
```

### 18.2 参数覆盖优先级

固定优先级如下，越靠后优先级越高：

```text
device_library.yaml 默认值
  -> system_templates.yaml 模板默认值
  -> scenario_catalog.yaml 场景类型默认值
  -> scenario.yaml 用户覆盖
  -> Excel 表格覆盖
```

这样既能保证用户少填参数时可以快速试用，也能保证真实工程项目可覆盖默认参数。

### 18.3 校验规则

#### 场景层

1. `scenario.id` 不为空。
2. `system.template` 必须存在于 `system_templates.yaml`。
3. `scenario_type` 如果填写，必须存在于 `scenario_catalog.yaml`。
4. `currency` 必须填写或能从默认配置补齐。

#### 能源载体层

1. 所有 `demand`、`input`、`resource` 必须存在于 `carrier_dictionary`。
2. 启用的用户需求必须有月度总量或典型日曲线。
3. 未启用的载体不应被标记为必填。
4. 设备输入输出载体必须能在场景能源配置中找到。

#### 数据层

1. 8760 模式必须有 8760 行。
2. 月典型日模式必须有 12 个月，每个月 24 小时曲线。
3. `month` 必须为 1-12。
4. `hour` 必须为 1-24。
5. 负荷和资源可用量不应为负，除非字段明确允许负值。
6. 典型日权重之和应为 365，或等于用户声明的模拟代表天数。

#### 设备层

1. `library_id` 必须存在于 `device_library.yaml`。
2. `enabled=true` 的设备必须有容量上界或固定容量。
3. 当前后端不支持的设备不能进入 `current_cchp` 求解。
4. 设备所需关键参数必须能由默认库或用户覆盖补齐。

#### 价格层

1. 启用外购能源时必须有价格或默认价格。
2. 分时价格必须覆盖 1-24 小时。
3. 容量费缺省为 0。
4. 单位必须可识别，第一版可先做字段校验，不做复杂自动换算。

#### 典型日层

1. `user_selected` 必须提供典型日文件。
2. `cluster_from_8760` 必须提供 8760 数据。
3. `monthly_template` 必须提供每月 1 个 24h 典型日。
4. 聚类依赖不可用时应 fallback 或给出明确错误。

### 18.4 面向用户的错误提示

错误信息应说明“哪里错、为什么错、怎么改”。

示例：

```text
错误：设备 electrolyzer 已启用，但当前系统模板 cchp_ehc_base 使用 current_cchp 后端，该后端不支持 hydrogen 载体。
建议：关闭 electrolyzer，或切换到支持 hydrogen 的系统模板。
```

```text
错误：05_用户负荷需求曲线中声明了 demand_id=steam，但 03_场景能源配置中没有启用 steam。
建议：在 03_场景能源配置中新增 steam，或删除该负荷曲线。
```

## 20. 命令行/API 调用入口设计

第一版建议新增 `design.py` 作为场景化系统设计入口，与现有论文实验入口 `run.py` 区分。

| 入口 | 用途 |
|---|---|
| `run.py` | 论文实验入口，服务方法对比和论文结果。 |
| `design.py` | 场景化系统设计入口，服务中期接口、用户配置和项目验收。 |

### 20.1 基本调用方式

#### 用 YAML 场景配置运行

```bash
uv run python design.py --scenario scenarios/songshan_lake/scenario.yaml --mode test
```

含义：读取 `scenario.yaml`，补齐默认设备库和系统模板，转换成当前 `case_config`，调用现有优化流程并输出设计结果。

#### 用 Excel 模板运行

```bash
uv run python design.py --excel scenarios/songshan_lake/raw_input.xlsx --mode test
```

含义：读取 Excel，转换成标准场景包，生成 `resolved_scenario.yaml`，调用优化并输出设计结果。

#### 只校验配置，不运行优化

```bash
uv run python design.py --scenario scenarios/songshan_lake/scenario.yaml --validate-only
uv run python design.py --excel 场景整理_某工业园区.xlsx --validate-only
```

用途：检查字段、能源载体、设备、价格、典型日是否完整，不跑优化。

#### 只生成典型日

```bash
uv run python design.py --scenario scenarios/songshan_lake/scenario.yaml --generate-typical-days
```

用途：用户提供 8760 数据时，只生成 `typical_days.csv` 和 `typical_day_report.md`。

#### 只转换 Excel

```bash
uv run python design.py --excel 场景整理_某场景.xlsx --export-scenario scenarios/xxx/
```

用途：把 Excel 转成标准场景包，供人工检查或批量运行。

#### 跑后验分析

```bash
uv run python design.py --scenario scenarios/songshan_lake/scenario.yaml --post-analysis full
```

用途：优化完成后选取代表方案，用 8760 数据逐日调度计算运行指标。

### 20.2 建议命令行参数

```text
--scenario PATH          读取 YAML 场景配置
--excel PATH             读取 Excel 场景模板
--mode test|quick|full|custom
--validate-only          只校验，不优化
--generate-typical-days  只生成典型日
--export-scenario PATH   将 Excel 转成标准场景包
--post-analysis MODE     后验分析模式：test/quick/medium/full
--methods METHODS        优化方法，例如 euclidean std economic_only
--nind INT               自定义种群规模
--maxgen INT             自定义迭代代数
--workers INT            并行进程数
--output PATH            输出目录
--overwrite              覆盖已有转换结果
```

参数优先级：

```text
命令行参数
  -> scenario.yaml 中的 optimization/output 配置
  -> optimization_defaults.yaml 默认配置
```

命令行参数优先级最高。例如：

```bash
uv run python design.py --scenario scenarios/songshan_lake/scenario.yaml --mode test --nind 20
```

这里 `--nind 20` 覆盖配置文件中的 `nind`。

### 20.3 内部执行流程

```text
main()
  -> parse_args()
  -> if excel: ExcelTemplateParser.to_scenario_package()
  -> ScenarioLoader.load()
  -> DefaultsResolver.resolve()
  -> SchemaValidator.validate()
  -> if validate_only: export validation report and exit
  -> TypicalDayGenerator.prepare()
  -> OptimizerAdapter.to_current_cchp_config()
  -> DesignOptimizer.run()
  -> ResultExporter.export()
  -> if post_analysis: PostAnalysisRunner.run()
```

伪代码：

```python
def main():
    args = parse_args()

    if args.excel:
        scenario_path = ExcelTemplateParser(args.excel).export_scenario_package(
            output_dir=args.export_scenario
        )
    else:
        scenario_path = args.scenario

    scenario = ScenarioLoader.load(scenario_path)

    resolved = DefaultsResolver(
        scenario_catalog="defaults/scenario_catalog.yaml",
        system_templates="defaults/system_templates.yaml",
        device_library="defaults/device_library.yaml",
        component_mapping="defaults/component_mapping.yaml",
    ).resolve(scenario)

    SchemaValidator.validate(resolved)

    if args.validate_only:
        ResultExporter.export_validation_report(resolved)
        return

    TypicalDayGenerator.prepare(resolved)

    case_config = CurrentCCHPAdapter.to_case_config(resolved)

    result = DesignOptimizer.run(case_config, args)

    ResultExporter.export(result, resolved)

    if args.post_analysis:
        PostAnalysisRunner.run(result, resolved)
```

```csv
solution_id,selection_rule,annual_cost,matching_index,device_id,device_name,capacity_value,unit
```
