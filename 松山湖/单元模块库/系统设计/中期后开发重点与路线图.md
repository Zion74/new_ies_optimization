# 中期后开发重点与路线图

## 1. 当前状态

中期阶段已经完成“标准化单元模块库接口 + 三场景验收闭环”的最小可交付版本：

- 松山湖、德国两个冷热电 CCHP 场景已通过 `current_cchp` 后端完成容量配置闭环；
- 烟厂场景已作为差异化工业场景接入 `future_generic / linear_energy_hub` 通用后端；
- 烟厂已完成 24h 真实调度求解，并额外完成 test 级轻量双层验证：外层容量候选搜索 + 内层调度求解；
- 已形成验收报告、使用说明书、Excel 场景整理模板、默认设备库、通用组件映射和一键检查脚本。

中期后的开发目标不是继续堆单个场景 demo，而是把当前原型推进为“可规模化接入 15+ 场景、可被合作课题组容量优化器稳定调用”的通用模型接口。

## 2. 总体路线

```mermaid
flowchart LR
    A["用户/师弟整理 Excel 场景"] --> B["ExcelScenarioParser 数据清洗与导出"]
    B --> C["标准 scenario.yaml + 时序 CSV"]
    C --> D["DefaultsResolver 补齐设备库参数"]
    D --> E["GenericBackendPlanner 组件映射"]
    E --> F["GenericModelBuilder 标准系统对象"]
    F --> G["给定容量后的调度仿真接口"]
    F --> H["capacity_variables 容量变量空间"]
    H --> I["合作课题组或内置容量优化器"]
    I --> G
    G --> J["容量结果、调度结果、转换类型统计、缺口报告"]
```

后续开发应围绕三条主线推进：

| 主线 | 目标 | 交付物 |
|---|---|---|
| 通用后端深化 | 把 `future_generic` 从验收原型推进到可扩展求解后端 | 标准系统对象、调度接口、动态容量变量、目标函数和约束接口 |
| 场景接入标准化 | 让 15+ 场景接入更快、更少 bug | Excel 容错、字段别名、数据完整性报告、缺口清单、一键验收 |
| 合作接口稳定化 | 让合作课题组可以按我们的对象和接口做容量优化 | API 文档、输入输出 schema、demo 调用脚本、版本化样例 |

## 3. 优先级 P0：通用双层优化闭环

### 3.1 正式化 GenericModelBuilder

当前 `GenericModelBuilder` 已能根据组件计划生成通用组件、能源母线和容量变量。后续需要继续补齐：

- 标准系统对象：统一表达 `components`、`buses`、`connections`、`time_series`、`parameters`、`capacity_variables`；
- 组件约束模板：Source、Sink、Transformer、GenericStorage、Source_plus_Transformer 的约束生成逻辑；
- 设备参数绑定：把设备库里的效率、COP、投资成本、容量上下界、储能能量容量等参数稳定映射到模型；
- 多能源载体单位边界：电、热、冷、蒸汽、天然气、氢等载体的单位和换算方式必须显式记录；
- 模型构建缺口：缺参数时不静默失败，而是输出可读的缺口报告。

### 3.2 给定容量后的调度接口

我们的责任边界应优先保证“给定容量后能跑运行调度”。建议稳定一个函数级接口：

```python
from generic_system import GenericSystem

system = GenericSystem.from_resolved(resolved, project_root=PROJECT_ROOT)
dispatch_result = system.solve_dispatch(
    capacities={
        "pv.capacity_kw": 5000,
        "steam_boiler.steam_capacity_t_h": 20,
    },
    month=1,
    periods=24,
    accept_default_bounds=True,
)
```

当前 P0 已落地的合作边界是：`system_object.json + capacity_variables.json/csv + GenericSystem.solve_dispatch(capacities)`。其中 `system_object.json` 统一表达场景、母线、组件、连接、时序引用、设备参数、容量变量和构建缺口；`capacity_variables` 既保留旧字段，也提供 `name / parameter / lb / ub / default_value / is_fixed / source` 等标准字段；`GenericSystem` 则给外部容量优化器提供“给定容量后运行调度”的 Python API。

调度接口至少输出：

- 求解状态：`optimal`、`infeasible`、`solver_error`；
- 目标值：运行成本、购能成本、弃能惩罚、排放成本等；
- 能流结果：各组件输入输出、母线平衡、储能 SOC；
- 缺口信息：缺少哪些参数、哪些约束暂未接入；
- 机器可读结果：JSON / CSV，方便合作课题组读取。

### 3.3 容量变量抽象

容量变量应由我们定义，因为我们负责对接用户和设备库。后续需要把 `capacity_variables` 做成正式 schema：

| 字段 | 说明 |
|---|---|
| `name` | 变量名，例如 `pv.capacity_kw` |
| `device_id` | 设备实例 ID |
| `parameter` | 容量参数名 |
| `unit` | 单位，例如 `kW`、`kWh`、`t/h` |
| `lb` / `ub` | 下界和上界 |
| `default_value` | 默认值 |
| `is_fixed` | 是否固定 |
| `source` | 来源：用户输入、设备库默认、验收默认、资料推导 |

这样才能支持后续“固定部分变量、优化另一些变量”的需求。

### 3.4 内置容量优化器的定位

合作课题组后续可能会做正式容量优化，但我们仍需要保留内置 demo 优化闭环，原因是：

- 验证模块库和调度模型本身可计算；
- 给合作课题组提供可运行参考；
- 在没有合作优化器时也能快速测试新场景；
- 中期/结题材料需要展示容量配置结果。

内置优化器建议从当前 test 搜索逐步升级：

1. `demo/random/de`：保留，用于快速 smoke test；
2. 单目标年化成本优化：优先实现稳定；
3. 多目标优化：成本、排放、源荷匹配度、可再生消纳等；
4. 多典型日加权：从 1 个 24h 切片扩展到 12 个月典型日；
5. 8760 全年验证：作为高可信结果或典型日结果复核。

## 4. 优先级 P1：场景接入标准化

### 4.1 Excel 解析和数据质量

后续要接入 15+ 场景，最大风险不是模型，而是输入表格不规整。Excel 解析器需要继续增强：

- 字段别名：支持“设备名称 / 设备名 / device_name”等常见写法；
- 数值容错：处理 `6.5,`、中文单位、空格、合并单元格、错位行；
- 缺失提示：告诉用户缺哪张表、哪列、哪几个月、哪几个小时；
- 重复检测：识别重复的月-小时-负荷类型；
- 自动导出清洗版：不覆盖原表，输出清洗副本和清洗日志。

### 4.2 输入数据完整性报告

每个场景导入后应自动生成完整性报告：

| 检查项 | 例子 |
|---|---|
| 负荷曲线完整性 | 是否为 12 个月 × 24h × N 类负荷 |
| 资源曲线完整性 | 光照、风速、温度、余热是否覆盖优化周期 |
| 月总量校核 | 典型日曲线加权后是否接近月总量 |
| 价格参数 | 是否有电价、气价、蒸汽价格或碳价 |
| 设备边界 | 是否有容量上界、储能能量容量、已有设备容量 |
| 单位一致性 | t/h、kg/h、kW、kWh、Nm3/h 是否可换算 |

### 4.3 典型日与 8760 数据策略

需要把数据粒度规则固化：

- 用户给 8760：程序可聚类生成典型日，也可保留全年调度验证；
- 用户给 12 个月典型日：按月典型日加权，是后续接入的推荐格式；
- 用户只给部分月份：允许接入，但必须标记为数据缺口或执行插值/合成；
- 用户只给月总量：可生成粗略典型日，但正式优化前必须提示可信度不足；
- 混合数据：生成数据完整性报告，由用户确认。

## 5. 优先级 P1：合作课题组对接接口

### 5.1 推荐交付对象

建议给合作课题组交付“标准系统对象 + 给定容量调度接口”，而不是让他们直接读我们内部散乱配置。推荐对象包括：

- `system_object.json`：组件、母线、连接、参数、容量变量；
- `capacity_variables.csv/json`：优化变量清单；
- `time_series/`：负荷、资源、价格时序；
- `solve_dispatch(capacities)`：给定容量后的调度仿真接口；
- `objective_terms.json`：成本、排放、匹配度等目标项定义；
- `constraints_report.csv`：模型约束和缺口说明；
- `demo_optimizer.py`：参考调用示例。

### 5.2 接口边界

建议边界如下：

| 工作内容 | 我们负责 | 合作课题组负责 |
|---|---|---|
| 用户场景输入规范 | 是 | 可反馈需求 |
| Excel 清洗与标准化 | 是 | 否 |
| 设备库和组件抽象 | 是 | 否 |
| 容量变量定义 | 是 | 可读取并优化 |
| 给定容量调度模型 | 是 | 调用 |
| 正式上层容量优化算法 | 提供 demo 和接口 | 主要负责 |
| 结果解释和转换类型统计 | 是 | 可使用 |

### 5.3 需要尽快确认的问题

后续应找导师或合作组确认：

1. 合作组希望调用 Python 类、JSON 文件，还是命令行 CLI？
2. 他们是否接受我们定义的 `capacity_variables`，还是需要适配他们已有变量命名？
3. 目标函数由谁定义？例如年化成本、排放、源荷匹配度是否都由我们提供？
4. 调度模型是由我们固定提供，还是他们需要直接访问 Pyomo/OEMOF 模型对象？
5. 最终验收需要“15 场景都真实求解”，还是允许部分场景停留在组件计划和缺口报告层级？

## 6. 优先级 P2：烟厂场景深化

烟厂已经能作为第三场景支撑中期验收，但正式工程计算还需要补齐：

- 蒸汽参数：压力、温度、焓值或 t/h 到 kW_th 的折算边界；
- 设备经济参数：投资成本、运维成本、寿命、年化系数；
- 容量上界：屋顶面积、设备间空间、已有设备、锅炉容量、余热上限；
- 资源曲线：太阳辐射、余热、温度补成完整 12 个月典型日或 8760；
- 价格曲线：24h 分时电价、天然气价格、可能的蒸汽或碳成本；
- 新增/已有设备标记：区分已建设设备、可改造设备和新增设备。

烟厂后续最好作为“工业蒸汽 + 余热回收”标准样例长期维护，避免每次新工业场景都重新摸索。

## 7. 优先级 P2：15 场景扩展

15 场景扩展不建议一次性全部写模型，而应按“模板覆盖 + 缺口报告 + 逐步求解”推进：

1. 先保证 15 场景都有 `scenario_type`、能源载体、默认模板和候选设备推荐；
2. 每个场景能导出组件计划和容量变量；
3. 对可数据化场景推进到 Level 3 调度求解；
4. 对暂时缺数据场景输出“不可求解原因”和“补齐项”；
5. 最后选择代表性场景做完整容量优化。

建议验收分级：

| 等级 | 含义 |
|---|---|
| Level 1 | 可解析 Excel/YAML，能源载体和设备清单可识别 |
| Level 2 | 可生成通用组件计划和容量变量 |
| Level 3 | 给定容量后可完成真实调度求解 |
| Level 4 | 可完成轻量容量搜索 + 内层调度 |
| Level 5 | 可完成正式多目标/多典型日容量优化 |

## 8. 推荐近期任务清单

建议中期后按以下顺序推进：

1. 已完成：固化 `system_object.json` 和 `capacity_variables.json/csv` 的 P0 schema；
2. 已完成：把 `solve_dispatch(capacities)` 包装成 `GenericSystem` Python API；
3. 下一步：把烟厂从 1 月 24h 扩展到 12 个月典型日加权；
4. 下一步：生成每个场景的数据完整性报告；
5. 下一步：补齐烟厂关键经济参数和蒸汽换算边界；
6. 下一步：写合作课题组对接 demo；
7. 下一步：选 3 到 5 个差异化场景做 Level 3/Level 4 验证；
8. 后续：再推进正式多目标容量优化。

## 9. 小结

中期前的重点是“证明三场景能跑通”；中期后的重点是“让场景接入、设备抽象、容量变量和调度接口变成稳定平台能力”。后续所有开发都应优先服务这四个能力：

- 快速接入新场景；
- 自动识别设备和能源转换类型；
- 稳定生成容量变量和标准系统对象；
- 给定容量后可靠完成调度仿真，并能被外部容量优化器调用。
