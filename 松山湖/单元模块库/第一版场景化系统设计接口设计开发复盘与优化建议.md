# 第一版场景化系统设计接口设计开发复盘与优化建议

更新时间：2026-05-24

## 1. 复盘范围

本复盘覆盖第一版场景化系统设计接口从需求沉淀到 quick 模式跑通的设计与开发工作，重点检查：

- 用户输入是否清晰。
- 单元模块库抽象是否便于扩展。
- 当前代码是否能证明“调用单元模块库实现系统设计”。
- 松山湖和德国两个场景是否真正跑通。
- 哪些问题应在第二版优化前由用户审查确认。

## 2. 已完成的设计决策

| 决策 | 当前方案 | 评价 |
|---|---|---|
| 用户输入形态 | 内部以 YAML/JSON 为主，Excel 作为协作整理和展示模板 | 合理，便于程序读取，也便于师弟或课题组成员整理场景 |
| 场景与系统结构 | `scenario.yaml` 明确 `scenario`、`system.template`、`energy_carriers`、`data`、`prices`、`devices`、`optimization` | 输入边界清楚，暂不做动态拓扑生成 |
| 设备参数 | 默认设备库补齐技术经济参数，用户只覆盖必要参数 | 符合“最小输入 + 可自定义”的需求 |
| 能源载体 | 区分 `demands`、`inputs`、`resources`，并支持电、热、冷、氢、蒸汽、天然气等载体预留 | 可扩展性较好，能适配 15 类场景 |
| 典型日 | 支持已有典型日文件，也预留 `monthly_template` 和 `cluster_from_8760` 生成方式 | 能覆盖当前实验和后续用户输入差异 |
| 计算后端 | 第一版通过 `CurrentCCHPAdapter` 适配现有 CCHP 优化模型 | 工程风险最低，能快速证明闭环 |
| 输出结果 | 同时输出 CSV、Excel、Markdown、JSON | 兼顾程序追溯、人工审查和验收展示 |

## 3. 当前代码结构 Review

| 模块 | 职责 | Review 结论 |
|---|---|---|
| `design.py` | 命令行入口，串联场景加载、校验、优化和导出 | 职责清晰；已修复 `--mode quick` 优先级问题 |
| `scenario_loader.py` | 读取 YAML 场景配置 | 简洁可用；后续可增加 schema 版本迁移 |
| `defaults_resolver.py` | 合并设备库、系统模板、场景目录和优化默认值 | 第一版可用；后续应补充更严格的冲突检测 |
| `schema_validator.py` | 用户输入校验 | 能捕获缺文件、缺价格、设备后端不支持等问题；后续应把错误分为阻断、警告、建议 |
| `current_cchp_adapter.py` | 将通用场景映射到当前 `case_config` 字典 | 当前闭环关键模块；但它仍是 CCHP 专用适配器，不是最终通用模型构建器 |
| `design_optimizer.py` | 构建运行配置并调用现有优化器 | 接口清楚；后续可增加超时、失败重试和结果目录配置 |
| `result_exporter.py` | 导出标准设计结果包 | 已满足验收展示；后续可增加设备中文名、单位换算和方案筛选规则 |
| `typical_day.py` | 典型日模板和聚类生成 | 已预留方向；后续需根据真实 8760 数据验证聚类质量 |
| `excel_parser.py` | Excel 场景整理模板解析 | 能支撑协作输入；后续需要更完整地支持多 sheet 数据曲线 |

## 4. 本轮验证发现并修复的问题

| 问题 | 影响 | 处理 |
|---|---|---|
| 命令行 `--mode quick` 没有完全覆盖场景 YAML 中的 `optimization.methods` | 松山湖第一次 quick 只跑了 `euclidean`，没有按 quick 默认跑 `std + euclidean` | 已修改 `design.py`，显式传入 `--mode` 时重置 optimization 为该模式，再叠加命令行覆盖 |
| quick 模式真实耗时偏长 | 两个场景 quick 合计耗时约 25 分钟，不利于现场演示 | 记录为优化建议，建议增加 `demo` 模式 |
| 第三场景仍是占位 | 可证明接口预留，但不能证明第三真实场景可计算 | 记录为中期后续风险，需尽快接入第三真实数据或实现通用后端 |

## 6. 优化建议清单

| 优先级 | 建议 | 原因 | 是否建议立即做 |
|---|---|---|---|
| P0 | 明确第三场景验收口径：是“预留接口”还是“真实可计算场景” | 这会直接影响中期验收表述，避免过度承诺 | 是 |
| P0 | 若需要严格满足 3 个可计算场景，优先接入一个与 CCHP 兼容的第三场景 | 可以复用当前后端，最快补齐 3 场景计算证据 | 是 |
| P1 | 增加 `demo` 模式，例如 `nind=6, maxgen=3, methods=[euclidean]` | 现场演示和回归测试不应每次等待十几分钟 | 建议 |
| P1 | 修复旧版 `comparison_report.md` 的货币符号展示 | 松山湖应显示 CNY/¥，避免导师审查时误解 | 建议 |
| P1 | 将结果目录从 `Results/` 改为可配置的 `DesignResults/` 或支持 `--output` | 区分论文实验结果和接口设计结果，便于归档 | 建议 |
| P1 | 给 `schema_validator.py` 增加“未来后端可用但当前不可运行”的状态 | 现在只有错误/警告，不能很好表达电-氢模板这类预留场景 | 建议 |
| P2 | `design_summary.xlsx` 增加设备中文名、设备类型、能源输入输出和是否新增设备 | 更适合验收展示，也更贴近用户关心的配置结果 | 可后续 |
| P2 | 增加典型日聚类报告图和代表日权重可视化 | 用户提供 8760 数据时，需要解释典型日如何确定 | 可后续 |
| P2 | 增加统一的 `run_design_checks.py` | 一条命令完成 validate、dry-run、测试和结果文件检查 | 可后续 |
| P3 | 引入正式 JSON Schema 或 Pydantic 校验 | 当前轻量校验够用，但字段多后需要更强约束 | 后续 |

## 7. 建议的第二版开发路线

### 路线 A：优先服务中期验收

1. 确认第三场景验收口径。
2. 若要求 3 个真实可计算场景，则选择一个与当前 CCHP 后端兼容的冷热电园区类案例。
3. 为第三场景补齐 `scenario.yaml`、负荷数据、典型日文件和价格参数。
4. 使用 `quick` 或新增 `demo` 模式跑通并补充本报告。
5. 修复货币展示和结果目录归档问题。

### 路线 B：优先服务最终 15 场景扩展

1. 把 `component_mapping.yaml` 扩展为真正的组件映射层。
2. 设计 `GenericModelBuilder`，按设备输入/输出载体自动生成 Pyomo/OEMOF 组件。
3. 先实现电-氢加氢站和工业蒸汽两个非 CCHP 模板。
4. 再把 15 类场景逐步映射到这些模板。
5. 最后把 Excel 模板升级为“场景信息 + 负荷曲线 + 资源曲线 + 设备覆盖参数”的完整输入包。

## 8. 需要用户审查确认的问题

- 第三场景中期是否必须真实跑通，还是本阶段允许“模板和接口预留，后续接入真实数据”？
- 如果要快速补齐第三可计算场景，是否优先选一个与松山湖/德国相近的冷热电园区案例，而不是直接做氢或蒸汽？
- quick 模式是否可以新增更小的 demo 参数，专门用于验收现场演示？
- 结果展示 Excel 是否需要按“方案维度”重新排版，例如一行一个推荐方案，设备容量横向展开？
- 后续通用建模层优先支持电-氢，还是工业蒸汽/燃气需求？

## 9. 总体评价

第一版设计是合理的：它没有急于重写优化模型，而是先把“用户输入规范、默认设备库、场景模板、当前模型适配、结果输出”这条最关键的工程链路打通。这样可以在中期阶段拿出可运行证据，也为后续 15 类场景扩展留下接口。

当前最大的风险不是松山湖和德国能否计算，而是第三场景和最终 15 场景需要从 CCHP 专用适配器升级到通用模型构建器。因此，下一步应先由用户确认第三场景验收策略，再决定是走“快速补齐第三可计算案例”还是走“通用后端优先”的路线。
