# 第一版场景化系统设计接口闭环验证报告

更新时间：2026-05-25

## 1. 验证目标

本报告用于证明“单元模块库构建”中期任务的第一版闭环已经跑通：

- 提供标准化、通用化的单元模块库接口代码。
- 在给定场景、系统结构、负荷数据、典型日文件和优化参数后，通过调用单元模块库与现有优化模型完成系统设计。
- 输出设备容量配置、目标函数结果、Pareto 解、解析后的完整场景配置和输入校验报告。
- 本轮以松山湖、德国、松山湖卡诺电池扩展三个真实可计算场景作为验证对象；第三场景先用已有松山湖真实数据与卡诺电池结构差异补齐，后续可替换为师弟整理的真实 Excel 场景。

## 3. 第一版接口调用链

```mermaid
flowchart LR
  A["用户输入: scenario.yaml / Excel"] --> B["ScenarioLoader / ExcelScenarioParser"]
  B --> C["DefaultsResolver: 合并默认设备库、系统模板、15类场景目录"]
  C --> D["SchemaValidator: 校验负荷、典型日、价格、设备参数"]
  D --> E["CurrentCCHPAdapter: 转为现有 case_config 形态"]
  E --> F["DesignOptimizer: 调用 run_comparative_study"]
  F --> G["cchp_gaproblem + operation: 容量优化与典型日调度"]
  G --> H["ResultExporter: 标准结果包"]
```

第一版的关键边界是：接口层负责把用户场景输入转换成标准模型调用参数，现有 CCHP/OEMOF 模型仍作为当前可运行后端。后续扩展到氢、蒸汽、燃气需求等场景时，需要把 `component_mapping.yaml` 中的设备抽象映射到通用 Pyomo/OEMOF 组件生成器。

## 4. 验证环境与 quick 模式参数

本轮验证日期为 2026-05-24，运行入口为仓库根目录下的 `design.py`。

quick 模式由 `ies_design/defaults/optimization_defaults.yaml` 提供默认参数：

| 参数 | 值 |
|---|---:|
| `mode` | `quick` |
| `nind` | 20 |
| `maxgen` | 20 |
| `workers` | 4 |
| `methods` | `std`, `euclidean` |
| `inherit_population` | `true` |
| `pool_type` | `Process` |

本轮修复了一个接口优先级问题：当命令行显式传入 `--mode quick` 时，应使用 quick 模式默认方法 `std + euclidean`，而不是被场景 YAML 中的 `optimization.methods` 覆盖。修复后两个场景均按 quick 默认方法完整执行。

## 8. 可展示给中期验收的结论

建议对外表述为：

> 已完成单元模块库第一版场景化系统设计接口。接口支持以 YAML/Excel 描述场景、系统结构、能源载体、负荷数据、典型日和设备参数；程序可自动调用内置设备参数库补齐缺省参数，转换为当前优化模型配置，并输出设备容量、目标值、Pareto 解和 Excel 结果表。当前已在德国、松山湖基础 CCHP、松山湖 CCHP + 卡诺电池扩展三个真实可计算场景上完成验证；后续电-氢/工业蒸汽等更独立场景可在已预留的 15 类场景目录与通用后端基础上接入。

## 9. 当前限制

- 当前真实可计算后端仍是 `current_cchp`，可以稳定覆盖冷热电 CCHP 类场景和卡诺电池扩展；氢、蒸汽、燃气需求等场景还需要通用调度求解后端。
- 第三真实可计算场景当前与松山湖共享负荷/资源数据，结构差异来自卡诺电池扩展；后续师弟 Excel 到位后可新增更独立的真实场景。
- quick 模式虽然比 full 小，但仍可能耗时较长；现场演示建议优先使用 `demo` 模式。
- 旧版 `comparison_report.md` 的货币展示已修复为按场景货币输出；验收时仍建议优先看 `design_report.md` 和 `design_summary.xlsx`。

## 11. 第二版补充：GenericModelBuilder

第二版新增 `GenericModelBuilder`：

- 路径：`松山湖/单元模块库/ies_design/generic_model_builder.py`
- 输入：已解析并补齐默认库的场景配置。
- 过程：调用 `GenericBackendPlanner` 生成通用组件计划，再构建通用模型组件规格。
- 输出：
  - `generic_model_components.json`
  - `generic_model_build_gaps.csv`
  - `generic_model_build_report.md`
- 当前能力：
  - 生成能源母线、负荷 Sink、Source、Transformer、GenericStorage 等组件规格。
  - 抽象每个启用设备的动态容量变量。
  - 在 `oemof.solph` 可用时尝试构建 `EnergySystem` 节点层。
  - 暂不执行调度求解和外层容量优化。

后续路线已经明确：把 `capacity_variables` 接入动态容量优化器，使不同场景根据启用设备自动形成不同数量的优化变量，再由 GenericModelBuilder 对每个候选容量方案构建/更新调度模型并求解。

## 12. 第二版补充：GenericDesignOptimizer

第二版继续新增 `GenericDesignOptimizer`：

- 路径：`松山湖/单元模块库/ies_design/generic_design_optimizer.py`
- 输入：`GenericModelBuilder` 生成的动态容量变量空间。
- 当前能力：
  - 不再固定 9 个 CCHP 容量变量，而是按场景启用设备自动生成变量数量。
  - 通过 `--run-generic-design --generic-search-levels 0 0.5 1` 运行轻量候选容量搜索。
  - 调用 `GenericDispatchModel.evaluate()` 输出设备容量映射、写回 `applied_capacities` 后的通用组件规格、投资成本近似、构建缺口和 `build_only` 状态。
  - 导出 `generic_design_solutions.json`、`generic_design_solutions.csv`、`generic_design_report.md`。
- 已纳入一键检查：

```powershell
rtk uv run python run_design_checks.py
```

本阶段的边界必须明确表述：`GenericDesignOptimizer` 已经完成“动态容量变量 -> 候选容量方案 -> 通用组件规格容量应用 -> 通用模型构建层评价 -> 报告导出”的接口闭环，并可选求解真实调度切片；当前真实切片已覆盖电网、PV、电储能、电热泵、电制冷、真实电/热/冷负荷和 COP 转换。完整 CHP、吸收式制冷、冷热储能、氢/蒸汽 OEMOF/Pyomo 调度求解仍未完成，尚未形成真正的通用双层优化结果。下一阶段需要把多输入多输出组件和外层 NSGA-II/DE 容量优化器逐步补齐。

## 13. 第二版补充：GenericOemofFactory

本轮新增 `GenericOemofFactory`：

- 路径：`松山湖/单元模块库/ies_design/generic_oemof_factory.py`
- 能力：
  - 把 `applied_capacities` 绑定到 OEMOF `Source` / `Transformer` / `GenericStorage` 的容量参数。
  - 返回可审查的 `node_specs`，用于确认每个组件的 `nominal_value` 和储能容量。
  - 返回可审查的 `dispatch_summary`，用于确认购电、PV、负荷供给和储能库存等调度结果汇总。
  - 已通过最小电力调度 smoke test：电力负荷 + 电网 Source + GLPK 求解，目标值可计算。
- 当前边界：
  - 已证明通用容量变量可以进入 OEMOF/Pyomo 节点层。
  - 已开始接入真实场景电/热/冷负荷、电价、太阳辐射、PV 容量、电储能容量、热泵容量和电制冷容量，并可求解 `grid_electric` / `grid_pv_electric` / `grid_pv_storage_electric` / `grid_pv_storage_heat_cool` 最小调度切片。
  - 电/热/冷储能已从单一功率变量扩展为“功率容量 + 能量容量”双变量；能量容量上界可由场景显式提供，也可由设备库默认储能时长推导。
  - 还没有把真实场景的 CHP、吸收式制冷、冷热储能、氢/蒸汽和多输出约束完整接入通用求解。
  - 松山湖/德国真实优化结果仍以 `current_cchp` 后端为准。

## 14. 第二版补充：GenericDispatchInputs

本轮新增 `GenericDispatchInputs`：

- 路径：`松山湖/单元模块库/ies_design/generic_dispatch_inputs.py`
- 能力：
  - 从 resolved scenario 的 `data.load_file` 读取真实 CSV。
  - 按 `data.column_mapping.ele_load_kw` 提取前 24 小时电负荷。
  - 按 `prices.electricity.value` 设置电网购电成本。
  - 按太阳辐射、温度和外层 PV 容量变量估算 PV 固定出力。
  - 构造 `electricity`、`heat`、`cooling` 母线，`electricity_demand` / `heat_demand` / `cooling_demand`，`grid_electricity` Source、PV 固定出力 Source、`electric_storage` 储能、弃电 Sink、电热泵和电制冷机。
  - 已通过 `GenericOemofFactory.solve_dispatch()` 求解松山湖真实 `grid_electric`、`grid_pv_electric`、`grid_pv_storage_electric` 与 `grid_pv_storage_heat_cool` 调度切片，并验证 PV、储能、热泵和电制冷容量能够进入真实调度求解层。
- 验收意义：
  - 通用后端已经从“组件层可构建”推进到“真实数据驱动的最小调度子问题可求解”。
  - 该结果仍不是完整冷热电系统设计结果；它是“真实冷热电负荷 + 单输入单输出转换组件”已可求解的通用后端推进证据。
