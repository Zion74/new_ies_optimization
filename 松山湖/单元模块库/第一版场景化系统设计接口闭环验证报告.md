# 第一版场景化系统设计接口闭环验证报告

更新时间：2026-05-24

## 1. 验证目标

本报告用于证明“单元模块库构建”中期任务的第一版闭环已经跑通：

- 提供标准化、通用化的单元模块库接口代码。
- 在给定场景、系统结构、负荷数据、典型日文件和优化参数后，通过调用单元模块库与现有优化模型完成系统设计。
- 输出设备容量配置、目标函数结果、Pareto 解、解析后的完整场景配置和输入校验报告。
- 本轮以松山湖和德国两个真实可计算场景作为 quick 模式验证对象；第三类场景已在场景目录和系统模板中预留，真实数据与通用后端后续接入。

## 2. 中期要求与当前实现对应关系

| 中期要求 | 第一版实现情况 | 证据 |
|---|---|---|
| 标准化、通用化的单元模块库代码 | 已实现设备库、系统模板、场景目录、组件映射、场景加载、默认参数补齐、校验、优化适配、结果导出 | `ies_design/defaults/*.yaml`、`design.py`、`ies_design/*.py` |
| 给定场景与系统结构作为初始化配置 | 已支持 `scenario.yaml` 输入，也支持 Excel 场景模板解析后导出 YAML/JSON | `ies_design/scenarios/*/scenario.yaml`、`excel_parser.py` |
| 调用单元模块库模型进行系统设计 | 已通过 `design.py` 读取场景，合并默认设备库和系统模板，转换为当前 CCHP 后端配置，再调用优化器 | `DesignOptimizer`、`CurrentCCHPAdapter` |
| 输出配置结果 | 已输出推荐方案、设备容量、目标值、Pareto 解、Excel 展示表和解析后的场景配置 | `design_report.md`、`design_summary.xlsx`、`pareto_solutions.csv` |
| 覆盖 3 种典型系统/场景 | 当前可计算闭环覆盖松山湖、德国两个真实场景；第三类电-氢/工业蒸汽等场景已在模板和 15 类场景目录中预留，但尚未接入真实数据和通用建模后端 | `scenario_catalog.yaml`、`system_templates.yaml`、`third_placeholder/scenario.yaml` |
| 暂不考虑系统拓扑动态生成 | 第一版按用户给定 `system.template` 选择固定系统结构，不自动生成拓扑 | `system_templates.yaml` |

结论：本轮已经完成“给定配置 -> 调用单元模块库 -> 优化计算 -> 输出容量配置”的第一版工程闭环。若严格按“3 个真实可计算场景”验收，第三场景还需要后续接入真实数据与通用后端；但按照当前讨论口径，本阶段先以松山湖和德国两个真实场景完成可运行验证。

## 3. 第一版接口调用链

```mermaid
flowchart LR
  A["用户输入: scenario.yaml / Excel"] --> B["ScenarioLoader / ExcelScenarioParser"]
  B --> C["DefaultsResolver: 合并默认设备库、系统模板、15类场景目录"]
  C --> D["SchemaValidator: 校验负荷、典型日、价格、设备参数"]
  D --> E["CurrentCCHPAdapter: 转为现有 case_config 形态"]
  E --> F["DesignOptimizer: 调用 run_comparative_study"]
  F --> G["cchp_gaproblem + operation: 容量优化与典型日调度"]
  G --> H["ResultExporter: 标准结果包"]
```

第一版的关键边界是：接口层负责把用户场景输入转换成标准模型调用参数，现有 CCHP/OEMOF 模型仍作为当前可运行后端。后续扩展到氢、蒸汽、燃气需求等场景时，需要把 `component_mapping.yaml` 中的设备抽象映射到通用 Pyomo/OEMOF 组件生成器。

## 4. 验证环境与 quick 模式参数

本轮验证日期为 2026-05-24，运行入口为仓库根目录下的 `design.py`。

quick 模式由 `ies_design/defaults/optimization_defaults.yaml` 提供默认参数：

| 参数 | 值 |
|---|---:|
| `mode` | `quick` |
| `nind` | 20 |
| `maxgen` | 20 |
| `workers` | 4 |
| `methods` | `std`, `euclidean` |
| `inherit_population` | `true` |
| `pool_type` | `Process` |

本轮修复了一个接口优先级问题：当命令行显式传入 `--mode quick` 时，应使用 quick 模式默认方法 `std + euclidean`，而不是被场景 YAML 中的 `optimization.methods` 覆盖。修复后两个场景均按 quick 默认方法完整执行。

## 5. 松山湖场景验证

### 5.1 输入

| 项目 | 内容 |
|---|---|
| 场景配置 | `松山湖/单元模块库/ies_design/scenarios/songshan_lake/scenario.yaml` |
| 场景 ID | `songshan_lake` |
| 场景名称 | 松山湖科研产业园 |
| 系统模板 | `cchp_ehc_base` |
| 用户负荷 | 电、热、冷 |
| 能源输入 | 天然气 |
| 资源/环境 | 太阳能资源、温度 |
| 负荷数据 | `data/songshan_lake_data.csv` |
| 典型日文件 | `data/songshan_lake_typical.xlsx` |
| 货币 | CNY |

### 5.2 运行命令

```powershell
rtk uv run python design.py --scenario "松山湖\单元模块库\ies_design\scenarios\songshan_lake\scenario.yaml" --mode quick
```

### 5.3 输出目录

```text
Results/design__songshan_lake__quick__20260524_160100
```

### 5.4 运行结果摘要

| 方法 | Pareto 解数量 | 最低年化成本 | 最优匹配度 |
|---|---:|---:|---:|
| Std | 20 | 1,421,918.38 | 79.2295 |
| Euclidean | 20 | 1,551,139.47 | 33.8555 |

标准推荐方案来自 `design_report.md`：

| 推荐类型 | 方法 | 原方案 ID | 年化成本 | 匹配度 |
|---|---|---:|---:|---:|
| `min_cost` | Std | 16 | 1,421,918.38 | 117.1767 |
| `min_matching` | Euclidean | 5 | 2,218,107.87 | 58.4679 |
| `knee_point` | Euclidean | 17 | 1,618,693.02 | 70.5271 |

松山湖 quick 验证结论：场景 YAML 可以被解析、默认设备参数可以补齐、现有 CCHP 后端可以完成双目标优化，并输出面向验收的容量配置结果包。

## 7. 标准结果包

两个场景均输出以下标准文件：

| 文件 | 作用 |
|---|---|
| `pareto_solutions.csv` | 汇总各方法 Pareto 解，包含经济成本、匹配度和设备容量 |
| `design_summary.csv` | 推荐方案长表，便于多能源载体和多设备扩展 |
| `design_summary_wide.csv` | 推荐方案宽表，便于人工查看 |
| `design_summary.xlsx` | Excel 展示版推荐方案，可用于验收汇报 |
| `design_report.md` | 场景化系统设计结果报告 |
| `resolved_scenario.json` | 合并默认库后的完整场景配置，便于追溯输入 |
| `validation_report.md` | 输入校验报告 |
| `comparison_report.md` | 现有优化器生成的方法对比报告 |
| `Pareto_Comparison.png` | Pareto 对比图 |

这批文件可以证明接口已经把“用户输入”和“优化输出”分离：用户侧只需要关心场景配置、负荷数据、典型日和可选设备参数；程序侧负责调用默认参数库、优化模型和导出器。

## 8. 可展示给中期验收的结论

建议对外表述为：

> 已完成单元模块库第一版场景化系统设计接口。接口支持以 YAML/Excel 描述场景、系统结构、能源载体、负荷数据、典型日和设备参数；程序可自动调用内置设备参数库补齐缺省参数，转换为当前优化模型配置，并输出设备容量、目标值、Pareto 解和 Excel 结果表。当前已在松山湖和德国两个真实冷热电场景上通过 quick 模式验证，后续第三类真实场景可在已预留的 15 类场景目录与电-氢/工业蒸汽模板基础上接入。

## 9. 当前限制

- 当前真实可计算后端仍是 `current_cchp`，可以稳定覆盖冷热电 CCHP 类场景；氢、蒸汽、燃气需求等场景还需要通用组件构建器。
- 第三场景目前是接口预留和需求占位，不应对外宣称已经完成真实优化计算。
- quick 模式虽然比 full 小，但每个真实场景仍需要约 12 分钟，演示场景建议增加更轻量的 `demo` 模式。
- 旧版 `comparison_report.md` 仍沿用原优化器的货币展示逻辑，验收时建议优先看 `design_report.md` 和 `design_summary.xlsx`。
